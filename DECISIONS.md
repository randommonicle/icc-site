## D-001 — Multi-page static front end, built with Astro
**Status:** Accepted (front-end tool resolved: Astro, June 2026)

The public site becomes a proper multi-page static site so each page is independently crawlable and can target its own search terms — the foundation of the SEO strategy (DESIGN §4, §9).

## D-002 — Supabase (managed Postgres) for the operational backend
**Status:** Accepted

Invoicing, payments, calendar sync, a client database, and marketing automation need persistent relational data, authenticated access, and background processing. Netlify Blobs is a key-value store and is not the right home for that. Supabase provides Postgres, admin auth, file storage for job photos, and an API without running servers. Netlify Blobs remains only for the Phase 0 PoC until Phase 2 migrates bookings into Postgres. (Consistency bonus: the ASH app and PropOS already use Supabase, so the conventions transfer.)

## D-004 — Stripe for payments; no card data stored locally
**Status:** Accepted

Stripe handles card security, so no card data is ever stored on the platform, keeping ICC out of scope for the heaviest payment-security obligations. Covers the deposit at booking and the balance on completion. True open-banking links are heavier and parked as optional/later (not needed to take deposits).

**Addendum (June 2026) — processor kept swappable; Revolut Merchant is a live alternative.** Mark is considering **Revolut Pro** (the sole-trader account) for the business banking. That does not change this decision and is compatible with it: the **card processor** and the **receiving bank account** are different layers. Two viable processor strategies, to choose at Phase 3:

- **Stripe** (default): best API/ecosystem for a custom embedded deposit-plus-balance flow, serves the website and the field app identically, and pays out to whatever bank account Mark nominates — **including Revolut Pro** (UK sort code + account number). Slightly higher UK card fees (~1.5% + 20p).

Open banking / "pay by bank" (e.g. via the Revolut Pay bank route) is the low-fee option worth considering for the **deposit** specifically.

**Design rule locked now:** the payment processor sits **behind our own server-side API (D-003); the website and field app never call the processor directly.** So Stripe ↔ Revolut Merchant (or adding pay-by-bank) is a server-side swap, not a client rebuild — the choice is not a one-way door, and we don't have to make it until Phase 3. ## D-007 — Single source of truth for AI model names; Sonnet for text, Opus only for vision
**Status:** Accepted

The cost discipline from ASH/PropOS applies here. Sonnet handles all text; Opus is used only when the latest user message contains an image (visual understanding genuinely needed). Model names must not be hardcoded across scattered call sites — once there is a backend, route them through one config value. Already partly implemented in `chat.js`.

**Addendum (12 June 2026) — vision tracks the current best Opus; bumps are deliberate, not automatic.** The vision slot in `shared/config/models.js` is pinned to the **best available Opus** (now `claude-opus-4-8`, up from `claude-opus-4-5`). Two reasons it is worth always being on the top Opus for image analysis: high-resolution image understanding arrived with Opus 4.7 and is exactly what photo-based carpet assessment needs; and the Opus tier is **flat-priced at $5/$25 per MTok across 4.5–4.8**, so "always the best Opus" is cost-neutral within the tier (the only cost wrinkle is that high-res images consume more image tokens per photo — pennies at one photo per turn). Text stays on Sonnet (`claude-sonnet-4-6`), already the current Sonnet.

The mechanism is a **deliberate one-line pin, not auto-detection.** We explicitly rejected code that fetches "the latest" model and switches automatically: a new model can shift tone, escalation propensity, citation and refusal behaviour, and silently swapping the model that gives damage-risk advice is precisely the D-019 failure mode. Every AI change in this project is deploy-preview-verified by a human before it reaches customers (4b/4c), and a model bump is no different. So the policy is "vision = current best Opus", realised as: change the one line in `models.js` when a newer Opus lands **and** a preview photo assessment confirms it still reads well. The single-source-of-truth (this D-007) is what makes that a trivial, low-friction change while keeping the human gate. (Operational watch: Opus 4.8 defaults `effort=high` on the API; if a vision turn's latency or cost creeps up, set `effort` lower on that call.)

## D-014 — One monorepo for the whole ICC platform (site + app + backend + shared contract)
**Status:** Accepted (June 2026)

The public website, the field app, the backend/serverless functions, and the shared API contract all live in this single repository. This is the natural consequence of D-003 and D-012: the website and the field app are two clients of one product, not two products.

Reasoning:
- One product, one repo. This is the dividing line from the ASH↔PropOS strategy, where separate repos are used precisely because those are separate products with separate commercial lives. The ICC site and ICC app are clients of the same platform, so they belong together.
- Single source of truth for the API contract. A `shared/` package (endpoint shapes, types) is imported by the site, the app, and the functions, so the compiler enforces D-012's "the two clients never diverge". Across two repos this needs a published versioned package or hand-duplication, and drift is exactly the failure mode we are avoiding (it is why PropOS needs the XR cross-repo tagging convention).
- Same win for D-006: the AI knowledge source lives in `shared/` and is consumed by site content, the assistant prompt, and the app.
- Bus factor: one clone, one doc set, one decisions/lessons log covering the whole platform.
- Atomic changes: an endpoint change plus both clients land in one PR, not coordinated cross-repo PRs.

The one real cost is two deploy targets (site → Netlify, app → Capacitor build). Handle it by scoping Netlify's build to changes under `site/` (and `shared/`) so an app-only commit never triggers a site deploy, and vice versa. The ASH repo already proves a Capacitor app + server + Supabase migrations coexist in one repo.

Target layout (created when Phase 2 starts, before the API exists to consume):
```
icc-platform/
├── site/                       public multi-page static site
├── app/                        field app (Capacitor)
├── functions/ (or server/)     API + AI proxy + serverless
├── shared/                     API contract types + AI knowledge source (D-006, D-012)
├── supabase/migrations/
└── docs/ + CLAUDE.md, ROADMAP.md, DECISIONS.md, LESSONS_LEARNED.md, NEXT_SESSION.md at root
```

Sessions stay separate by working on branches (existing discipline, D-010) or git worktrees — the monorepo makes separate site/app sessions easier, not harder, because each has the shared contract and docs to hand. The repo is currently named `icc-site`; rename to `icc-platform` when convenient (GitHub redirects the old URL) or leave it as a cosmetic mismatch. Do the monorepo restructure before building the Phase 2 API, so the contract is born in `shared/` rather than extracted later.

**Addendum (5 June 2026 — implementation):** backend folder resolved to **`server/`** (not `functions/`). Phase 2 Slice 0 moved `chat.js`/`bookings.js` to `server/netlify/functions/` (history preserved) on `chore/d014-monorepo`, updated the `netlify.toml` `functions` path, and repointed the test require paths — `node --test` green 8/8 locally, awaiting sign-off, not merged. ## D-015 — No quantified trust or marketing claims until independently substantiated
**Status:** Accepted (June 2026)

The public site must not show quantified track-record or trust metrics (completed-job counts, satisfaction percentages, star ratings) or superlative claims ("first", "guaranteed") unless each is independently substantiated and current. ICC is a new business with no track record yet, so figures like "500+ cleans" or "98% satisfaction" are unverifiable and breach ASA/CAP and the L-009 rule on repeating unverified claims. Capability facts that are simply true (for example "15+ carpet types", the six trading days, the 10% deposit) are fine, because they describe what the service is rather than a track record it has not earned.

Where a quantified metric would genuinely add value, it goes in only once there is a real, defensible source: a true completed-job count, or a verified review aggregate (which would also back an `aggregateRating` in the structured data). Implemented June 2026 on `feat/pre-cutover-polish`: the fabricated `500+`/`98%` tiles on the home and About pages were removed and replaced with capability facts, the "Guaranteed Results" and "first fully AI-assisted" claims were softened, and a grep-able `TODO(trust-stats)` anchor marks where substantiated metrics may later go. This is the site-side companion to L-009 (which governs the assistant) and is a hard gate on promoting the site off the Netlify name.

**Addendum (24 August 2026) — brand copy confirmed with Mark.** The homepage tagline is **"Intelligence you can trust"** (replacing "Established Trust, Superior Cleaning", which implied a track record a new business has not earned, the exact D-015 risk). ## D-019 — AI assistant grounding, source hierarchy, and human escalation
**Status:** Accepted in principle (11 June 2026); implementation in Phase 1 (knowledge consolidation) + Slice 4 (backend AI / handoff)

The assistant must not give incorrect information — above all, aftercare or stain advice that could physically damage a customer's carpet. The agreed design is a **grounded assistant with a two-lane source hierarchy and a safe "I don't know → escalate to a human" exit**, built as layered (defence-in-depth) guardrails rather than a single prompt instruction. Rationale: the model has no calibrated confidence, and an AI/web summary is exactly what caused the L-009 drift — so escalation is engineered by **category**, not by trusting the model to police itself.

**Source hierarchy (two lanes):**
- *Low-stakes / general* questions: vetted KB (D-006) → attributed web search → escalate.
- *Damage-risk / out-of-scope* questions: vetted KB only → **escalate to a human immediately** (never fall back to web for advice that could damage a carpet).

**Claude mechanisms (verified against the API, June 2026):**
- **Citations** — pass the vetted content as documents (or the cached system prompt, L-002) so Claude grounds and cites each claim to its source; an uncitable claim is itself a signal to soften or escalate.
- **Server-side `web_search`/`web_fetch`** — used only for low-stakes gaps, always **attributed** ("the manufacturer states…"), never asserted as ICC fact (L-009).
- **A custom `escalate_to_human` tool** — the model calls it when out of its depth; the *description must state when to call it* (out-of-KB, damage-risk, or no citable source), because recent Claude models under-reach for custom tools without explicit triggers. It returns the "I'll get the team to check" message and captures the question + contact as a lead.
- Constraint: Citations and forced-JSON structured outputs cannot be combined in one call, so prefer Citations + the escalation tool over a model-reported confidence score (which is unreliable anyway).

**Structural guards:** bound the assistant's remit to *educate + quote + book* (defer prescriptive treatment of valuable/delicate items to a professional assessment — escalate by design); optionally a cheap second-model (Haiku) verification pass that checks a safety-relevant draft against the KB before it is sent.

**Where it lands:** the build-out of D-006 (one vetted source feeds site + assistant) and the enforcement of L-009. The human-handoff half uses the **Slice 4 `messages` table** (draft → Mark approves → send) + admin review, so escalations become logged leads and Mark's corrections feed back into the KB. Today `chat.js` already does the simplest tier-1 (a cached system prompt = in-context grounding); value-ordered upgrade path: **structured KB → Citations → gated web tool → escalation tool + verification.**

**Addendum (11 June 2026) — three refinements settled while building Slice 4 (PRs #16/#17):**

- **No Haiku in the AI path.** The optional second-model (Haiku) verification pass is dropped. Using a model to police a safety-critical draft is exactly the un-calibrated-confidence problem D-019 exists to avoid; the engineered guards — Citations grounding (every claim tied to a source), the category-based `escalate_to_human` exit, and a bounded remit — are the defence-in-depth. If a second-model check is ever wanted it would be Sonnet, not Haiku, but the call is to leave it out. Supersedes the "optionally a cheap second-model (Haiku) verification pass" note above.
- **Citations are shown to the customer as links.** The Citations API returns, per grounded sentence, the source it came from. ## D-021 — Bookings cutover to Postgres (Slice 5b): env-gated, fail-CLOSED, hours folded in, admin reads both
**Status:** Accepted (Slice 5b, June 2026; built local-first + real-Supabase verified, enablement sign-off-gated)

`confirm_booking` and `check_availability` move off Netlify Blobs onto the Supabase `jobs`/`customers` schema (D-002): a confirmed booking upserts a customer (by email) and inserts a `jobs` row with `status='booked'`; availability is derived from the committed jobs; double-booking is the DB exclusion constraint (`jobs_no_double_booking`), not the Phase 0 read-then-write. This is the riskiest slice — the only one that changes live customer-facing behaviour — so it follows the 5a discipline (additive, env-gated, merge-is-a-no-op) with one deliberate inversion. Three load-bearing properties:

- **The booking write is FAIL-CLOSED — the deliberate inverse of the 5a escalation path.** 5a fails *open* because the email to Mark is the guaranteed channel. For a booking, **persistence *is* the deliverable**: a "Booking confirmed" email with no stored row is exactly the L-008 silent-vanish failure. So `handleBooking` persists **before** any PDF/email; the exclusion conflict (`23P01`) returns the existing `409`, and any other write failure returns `502` with **no email sent**. The client already surfaces both as its phone-number fallback (`index.html`), so no client change was needed. There is **no fallback to a Blobs write** on failure — that would reintroduce the dual-store split-brain this slice removes.
- **Env-gated by a single switch, so the merge is a production no-op.** `bookingsStoreIsPostgres()` (`BOOKINGS_STORE === "postgres"`) is the *one* source for store + availability + validation bounds, so they can never desync. Unset (or any other value), every path is byte-identical to the Phase 0 Blobs behaviour (the Blobs block is kept verbatim in the `else`). Enabling is a deliberate env set + redeploy in Netlify (the sign-off moment; env bakes at deploy, L-018); **rollback is unsetting it**. Note this differs from 5a's gate (`SUPABASE_*` presence), which is already set in production for handoffs — bookings need their own flag so they do not flip on at the 5a creds.
- **The 09:00–16:30 hours are folded in (the former Slice 5c) under the same flag.** The `jobs` schema enforces the confirmed trading day (start 9..15, every job ends by 16:00, ≤7 slots). `validateBooking(b, {latestStartHour,latestEndHour,maxSlots})` defaults to the Blobs bounds (17/18/9, byte-identical) and is called with 15/16/7 under Postgres, so a too-late/too-long slot is a clean `400` at validation, never a DB constraint error (`23514`) at insert. Availability uses the 9..15 grid under the flag. Store and hours therefore flip — and roll back — together.

Further decisions recorded:
- **No SQL RPC; two calls (customer upsert → job insert).** The exclusion constraint already makes double-booking impossible inside the single job insert, so the only gap an RPC closes is a rare orphan `customers` row when the job insert fails after the upsert — benign (a real prospect, holding no slot, deduped by the unique email next time, never touching the consent columns). Not worth a migration + pgTAP + a SECURITY DEFINER surface pre-launch.
- **No backfill; "fresh start, admin shows both".** Given near-nil real bookings, new bookings go to Postgres and the admin dashboard reads **both** stores and merges (dedupe by id — Postgres uuids and Blobs numeric ids are disjoint — newest-first), so legacy Blobs bookings stay visible. The Blobs read retires in a later tiny PR. (Verify Blobs holds no real *future* bookings before enabling; if it does, backfill them first.)
- **ex-VAT / deposit numerics stay NULL; `price_display` is authoritative.** The `BOOKING_READY` payload carries only a display string ("£475 + VAT") and the deposit is an inc-VAT figure (`pricing.js`), so parsing them into the `*_ex_vat` columns would store wrong-semantics numbers that later feed invoicing. The known surcharge (`out_of_area_surcharge_ex_vat` 15/0) *is* set. The deposit display is stashed in `notes` and recovered for the admin view. `TODO(slice5x/structured-pricing)` marks where the numerics get populated once the booking carries structured line items (e.g. via `/api/v1/quote`).
- **`jobs.postcode` made nullable** (its own migration + pgTAP + an inline catalog verification query) because the Phase 0 flow treats postcode as optional; the write resolves it best-effort (captured → regex-from-address → null). This is also where **D-011's out-of-area flag is finally derived + persisted server-side at booking** (`serviceArea.isOutOfArea`, erring toward charging on a missing/ambiguous postcode); the quoted *total* still rides on the assistant's display string until structured pricing lands.

## D-022 — Admin auth via Supabase Auth (Slice 5d): per-user login, allowlist, publishable-key verification
**Status:** Accepted + LIVE (Slice 5d, June 2026; merged PR #44 `31225e1`; operator login verified by Ben 15 June)

The admin dashboard moves off the shared `ADMIN_SECRET` Bearer onto **per-user Supabase Auth** (email + password). This is the shared identity model the field app reuses (D-012), and it removes the single shared secret that gated all of Mark's customer data.

- **Sign-in is the Supabase Auth password grant from the browser.** `admin.html` POSTs email+password to `{SUPABASE_URL}/auth/v1/token?grant_type=password` with the publishable key as `apikey`, and uses the returned `access_token` as the `Authorization: Bearer` on every `/api/*` call. The project URL + publishable key are **public by design** and embedded in the page (RLS + the allowlist are the controls, not key secrecy).
- **The server verifies the JWT, then checks an allowlist.** New `server/netlify/functions/adminAuth.js` `requireAdmin(event)` validates the Bearer token with a publishable-key client (`auth.getUser`) and requires the user's email to be in `ADMIN_EMAILS` (default: the two operators). `bookings.js` and `handoffs.js` call it in place of `safeEqual(ADMIN_SECRET)`. **Two layers on purpose:** public sign-ups are **disabled** in the project (so only the dashboard-created operators exist), and the allowlist is defence-in-depth so a stray/accidentally-created user still cannot read the dashboard. Fails closed: no token → 401, unconfigured → 503, invalid → 401, not-allowlisted → 403.
- **Hard swap, not dual-auth.** `ADMIN_SECRET` is no longer read by any function (kept as legacy in `.env.example`, removable from Netlify once 5d is confirmed live). The cutover is verified on a deploy preview before merge; rollback is a revert. A dual-auth transition (accept either the JWT or the old secret) was considered and rejected as keeping the very secret 5d removes; pre-launch with trivial rollback, the clean swap is safe. `safeEqual` is retained as a tested constant-time utility.
- **Why publishable-key verification, not the service-role client.** Verifying a *user* token with the publishable (anon) key is the standard pattern and keeps the service-role key strictly on the data path (`supabaseClient.js`). The publishable key has a code fallback so there is no new required env var; `SUPABASE_PUBLISHABLE_KEY` overrides it for rotation.

**Verification.** `node --test` 134 pass / 3 skip (`test/admin-auth.test.js` pins no-token/invalid/not-allowlisted/allowlisted/unconfigured; the handoffs handler auth tests updated). **NOT live-verified:** before merge, on a deploy preview — sign in as each operator (loads bookings + handoffs), a wrong password is rejected, and a token for a non-allowlisted user gets 403. **Status:** Accepted (erasure mechanism built; full erasure is a documented two-part procedure); retention period proposed, pending Mark + DP confirmation

Handoff-lead rows (`kind='human_handoff'`, `customer_id` null) hold customer PII (contact, question, conversation snippet, any draft reply) with, until now, no erasure path and no retention limit. This separates the two UK GDPR duties:

## D-041 — The accounting export's payments feed represents cash-in as two receipts (deposit + invoice balance), not one invoice at face value
**Status:** Accepted (Ben, 2026-09-13, ratifying the Beta 2e export proposal). Implements the D-026 build-note-6 accounting feed under [D-039](#d-039)'s operational-visibility boundary.

The accounting export (`GET /api/v1/accounting-export`) has two entities: an invoices REGISTER (documents raised, full face value) and a payments FEED (money actually received). Under Decision A ([BACKEND_PHASE1_PLAN.md](docs/BACKEND_PHASE1_PLAN.md)) an invoice's face value is the FULL job value with the paid deposit shown as a credit line, so the customer pays the deposit at booking (Stripe Checkout) and the BALANCE at completion (the invoice). Two separate money-in events, on two dates.

**Decision.** The payments feed emits **two receipts** for a deposit job: the deposit (dated `deposit_paid_at`, amount `deposit_ex_vat`, referenced by the Stripe payment_intent) and the invoice balance (dated `paid_at`, amount `full − deposit`, referenced by the invoice number). They sum to the full job value. A job with no paid deposit yields a single full receipt; an unpaid invoice is not a receipt (it stays in the register only).

**Why not invoices-only.** Listing paid invoices at face value would misdate the money (the full value would land on the completion date when part arrived at booking) and would drop the deposit as its own Stripe receipt, so the feed would not reconcile against the Stripe payouts. The two-receipts model reconciles and dates correctly without double-counting.

**Scope / boundary.** This is the generic feed for Mark's accountant / MTD tool (D-026 note 6), not in-platform accounting (the D-039 boundary holds). First cut excludes refunded deposits (`TODO(backend-phase1/accounting-refunds)`); a later slice emits refunds as negative events for period-accurate cash-in. No VAT (D-024).

## D-042 — The operational P&L is cash-basis: revenue is money received in the period (the D-041 receipts), expenses on incurred_on
**Status:** Accepted (Ben, 2026-09-13, on the recommended default while building Beta 3; override to accrual if preferred). Under [D-039](#d-039)'s operational-visibility boundary; reuses the [D-041](#d-041) receipts.

The P&L (`GET /api/v1/pnl`) answers "am I making money this period" at a glance (D-039), so it needs a revenue definition. Two options: cash-basis (money actually received in the period) or accrual (value completed/invoiced regardless of payment).

**Decision.** Cash-basis. Revenue = the D-041 payments feed (deposits + invoice balances/full) whose RECEIPT date falls in the period; expenses = cost rows whose `incurred_on` falls in the period; margin = revenue − expenses. Revenue is computed by `receipts.buildPayments` — the SAME function the accountant export uses — so the P&L margin reconciles with that feed and cannot silently diverge.

**Why cash-basis.** It matches how a sole trader feels the business (money in vs money out), reconciles with the Stripe payouts and the export, and needs no accrual bookkeeping (unbilled WIP, debtor ageing) that D-039 excludes. Period is UTC calendar days (`from`/`to`, default the current month). This is operational insight, not formal cash-basis tax accounting (Mark's accountant's job, D-026/D-039).

**Not this.** Accrual (recognise a completed job's full value at completion even if unpaid) would drift from the cash and from the export and would need debtor tracking; rejected for the light operational view. A future formal-accounts need stays external.


## D-043 — Migrations-before-deploy is a tracked pre-push hook, not a line in the handover

## D-045 — The operator assistant's turn runs in a Netlify background function; the admin page polls; a turn is stored for at most an hour or the next daily purge
**Status:** Accepted (Ben, 17 September 2026: "option three, it seems the most stable"). Resolves L-042. Supersedes the runtime shape in D-040's implementation contract ("stateless with bounded replay") and the "nothing is stored" line the endpoint's header used to carry; every other D-040 guardrail (operator-only, read-only through the facade, descriptive, spend-bounded, the atomic admission) stands unchanged.

**The problem.** D-040 ran the whole turn inside the request that admitted it, under an 8.5 s wall-clock deadline sized to Netlify's 10 s synchronous-function ceiling. The first live ride (16 September 2026, L-042) showed that leaves no headroom: the first turn after every deploy died cold, and a two-tool question died warm. Three options were weighed on 17 September: pre-warm the function on admin login (fixes only the cold turn), trim the turn (fixes only the warm two-tool case; prompt caching on the static operator block was already in place), or remove the ceiling by running the turn in a background function. Ben chose the third for stability.

**Gate checked before building.** The Netlify account is on the credit-based Personal plan (`type_slug: credit-personal`, read via the API) and the account capabilities report `background_functions: { included: true }`; the docs list background functions on the Free, Personal and Pro credit plans with a 15 minute limit and a 202 on invocation. No plan change was needed.

**The shape.**
- `POST /api/v1/operator-chat` keeps every gate in its D-040 order (origin policy, `requireAdmin`, per-IP, bounded body, configuration, the Postgres atomic admission) and then, instead of running the turn: prunes stale rows, stores the validated transcript as a `queued` row in the new `operator_turns` table (migration `20260917220000_operator_turns.sql`, RLS on with no policies, service role only) for the verified user, triggers `operatorTurn-background` over HTTPS with `{ turn_id }` and nothing else, and answers 202 `{ turn_id }`. The row is written before the trigger. The panel may send its own v4 uuid as `turn_id` (the idempotency key, below); a malformed one is a 400 before any budget is charged. The trigger origin is this deploy's own host (`DEPLOY_URL`, then `DEPLOY_PRIME_URL`, `URL`, `PUBLIC_SITE_URL`; never the request's Host header), so a branch deploy or preview triggers its own function.
- `operatorTurn-background.js` (the `-background` filename suffix; a v1 `exports.handler`) checks configuration, claims the row with a compare-and-set (`queued` to `running`, filtered on id AND status), runs the turn through `operatorTurnRunner.js` with the deadline anchored at its own entry, and records the result once (`running` to `done` / `stopped` / `failed`, again filtered on status, so the first terminal state stands). A throw mid-turn is recorded as `failed`.
- `GET /api/v1/operator-chat?turn=<uuid>` is the poll: `requireAdmin`, then the caller's own row only; an unknown or foreign id is a 404 (not a 403, so ids leak nothing). One shape per state: queued / running, done (content, usage, truncated), stopped (content, kind, usage), failed (a fixed line).
- `admin.html` polls after 3 s and then every 2 s, up to 90 s, then puts the question back with one message. The 90 s cap is pinned above the server's deadline by a test so the two cannot drift apart.

**The spend defence, named.** The background function's URL is public. Nothing runs there until the compare-and-set claim matched exactly one row; rows are written only by the gated endpoint, their ids are v4 uuids, and a replay, a platform retry of the async invocation, or a guessed id matches zero rows and spends nothing. That claim is the primary defence for the background function; the per-IP cap and the per-operator hourly budget stay on the endpoint that creates rows. The residual is the same as for every public function on the site: a flood of junk POSTs costs invocation credits and one cheap DB update each, never a model call. Proven on the local stack: ten concurrent clients on one queued row, exactly one claims, and the same update without the status filter lets all ten claim.

**The idempotency key (cross-agent review, GPT rounds 2 and 3, 17 September 2026).** A 202 that never reaches the browser (a dropped connection, the panel's 15 s hand-off timeout) would otherwise make the operator ask again and pay for a second turn. The panel therefore generates one `crypto.randomUUID()` per question and sends it as `turn_id`, keeping the key on its network-error and timeout branches so re-sending the same text resumes the same turn. The endpoint checks the key in this order: a known key for this caller answers 202 before admission (nothing admitted, stored or triggered); otherwise the normal path runs with the key as the row's id, so two sends racing past that read collide on the primary key (23505), which is re-read SCOPED to the caller and answered 202 only when the row is the caller's own. A key that collides with another operator's row is a 409 (`That turn id is already in use.`), never a 202: a 202 there would hand the caller a poll that 404s, an existence oracle for ids, and the guesser pays an admission each attempt. Rows are still written only by the gated endpoint, so the spend defence above is unchanged.

**Retention.** The transcript and the reply are stored for the life of the turn: the endpoint prunes rows older than an hour on every POST, and the daily `purge-handoffs` run prunes them as well (first in that run, so a handoff-purge failure cannot skip it). A row therefore lives an hour when questions keep coming, and in the worst case (the last question asked less than an hour before a daily run, then silence) until the following daily run, about 25 hours. The privacy notice needs no change: it describes what is sent to Anthropic and which fields, and the stored transcript carries the same fields (customer name and postcode at most) inside the business's own database.

**The deadline default moved from 8.5 s to 60 s.** Anchored in the background function, the deadline is no longer a platform bound; 60 s is a spend and patience bound (four model calls at most, each with the deadline as its abort signal), and `OPERATOR_TURN_DEADLINE_MS` still overrides it within 1000 to 60000. The Netlify environment carries no such variable, so the default applies.

**Log signatures for the operator's watch.** `operator turn queued: <id>` (the endpoint, happy path); `operator turn resumed by its key: <id>` and `operator turn already queued under its key: <id>` (the endpoint, a re-sent hand-off that resumed instead of paying again); `operator turn key collides with a row that is not the caller's: <id>` (the 409, a key reused across operators or guessed); `operator turn recorded: <kind> ms=<n> <id>` (the background function, the positive proof of a run); `operator turn not claimed: <reason> <id>` (a replay or retry, nothing spent); `operator turn stopped: <kind> ...` (the runner, as before). Two lines mean background mode is NOT active for the deploy and L-042 is back: `operator turn trigger answered 200, not 202: background mode is not active for this deploy`, or, when the synchronous run outlasts the 5 s trigger bound, `operator turn trigger failed: TimeoutError ...` followed by `operator turn claimed despite a failed trigger, the poll will find it: <id>` (the turn was already running inside the trigger call; since the 17 September cross-agent review the client is handed the id and polls for the result rather than being told 503 and asking, and paying, twice).

**Cost.** No new recurring job. Per turn: one background invocation for the length of the turn plus two to five cheap polls (Netlify: 2 credits per 10k requests, 10 credits per GB-hour), roughly 0.04 credits; about 25 credits a month at 20 questions a day against 1,000 included. Anthropic spend per completed turn is unchanged from the D-040 pricing.

**Relationships.** Extends D-040 (its guardrails unchanged); D-043's migration gate applies (the migration is applied to hosted and catalog-verified before the batch is pushed); the daily purge of D-023 gains a second, unregulated prune. Build record: `docs/OPERATOR_BACKGROUND_TURN_PLAN.md`.

## D-046 — Admin password recovery is Supabase Auth's own email recovery, driven from the admin page with the raw GoTrue REST it already uses; the redirect is the page's own origin
**Status:** Accepted (Ben, 18 September 2026, "yes to the password flow, I agree with all your suggestions", after the build, the local ride and the three reviews below; the roadmap item is his, 16 September 2026, after a reset by script). The hosted allowlist step and the hosted ride follow the merge. Extends Slice 5d (per-user Supabase Auth for the admin); every 5d control stands: sign-ups disabled, `ADMIN_EMAILS` checked server-side on every request.

**The problem.** The admin dashboard had no self-service recovery: an operator who forgot the password needed someone with the service-role key to run `scripts/admin-set-password.js` from a checkout holding the real `.env` (16 September 2026). That is a bus-factor and an out-of-hours problem for a two-person business, and the script's own header admitted a recovery email would land on a page that did not handle the token.

**The decision.** Use Supabase Auth's recovery flow as it is, from `admin.html`, with no new dependency and no server-side code: `POST /auth/v1/recover` with the email, GoTrue's one-time link back to the page, the session read from the URL fragment (the implicit flow; the page sends no PKCE challenge, and adding supabase-js to the page for PKCE alone was not worth a dependency), and one `PUT /auth/v1/user` with the new password. Three choices inside that:

- **The redirect target is the page's own origin plus `/admin`**, computed at request time, so one build serves the `.netlify.app` host and the real domain before and after the cutover. The cost is an owner step: each origin must be on the project's redirect allowlist, or GoTrue silently falls back to the Site URL and the link lands on the wrong page. Recorded in `docs/ADMIN_PASSWORD_RESET.md`, with the local stack mirroring it in `supabase/config.toml`.
- **The token is read once, wiped before use, held in memory only.** `history.replaceState` runs before the token is kept, so it never sits in the address bar, the tab history or a referrer; nothing logs it. After the password is saved the token is discarded and the operator signs in normally rather than being signed in from the recovery session, which keeps one sign-in path.
- **Honest messages, and no enumeration beyond what GoTrue itself exposes.** The success note says "if that address has an admin account" whichever way GoTrue answered (200 either way). GoTrue's per-address send limit answers 429 only for a real account, so the page reports "too many reset emails" for it rather than pretending a link was sent: that oracle lives in the API whatever the page says (measured on the local stack on 18 September 2026: a known address 200 then 429, an unknown one 200 twice), and with two admin addresses that are no secret it is not worth a lie to the operator (cross-agent review, GPT). An expired or reused link (GoTrue's `otp_expired` error fragment) gets its own message; GoTrue's own refusal text (project password policy, same as the old password) is rendered as inert text (L-003).

**Named residuals.** Recovery emails go through Supabase's built-in mailer until custom SMTP is configured (an owner option, not a gate): a low hourly cap and a generic sender that spam filters may hold. The client minimum of 8 characters is a one-line constant; the project's own policy applies on top. The recovery session is a real one-hour session for the account, and `requireAdmin` accepts any valid session whose email is allowlisted: whoever holds the link within the hour can act as that account against the admin API with or without changing the password (cross-agent review, GPT). That is the property of every email-recovery flow, so the reset email is a temporary sign-in credential and the mailbox is the thing to protect; the page narrows its own exposure by dropping the session the moment the operator leaves the recovery card (save or back), never logging or storing it, and never reading the refresh token at all. The reset link is a GET that verifies the token on the way through, so a mailbox that prefetches links could spend it before the operator clicks (the D-027 `booking-action` design avoided exactly this for its own token by putting it in a fragment the page POSTs); both admin mailboxes are Google Workspace, which does not prefetch, so this is recorded rather than built against. If it ever bites, the `{{ .TokenHash }}` email template with a `POST /auth/v1/verify` from the page removes it (independent review, 18 September 2026). The same review asked that the Site URL be confirmed as an ICC-controlled host before the first hosted use, since it is where a non-allowlisted origin's link lands; that is now the first line of the owner step.

**Verification.** Pinned in `test/admin-html-syntax.test.js` (the pin proven red by removing the wipe) and ridden end to end on 18 September 2026 against the local stack: request, email (Mailpit), link, recovery card with the fragment wiped, the three refusals, the save, the old password refused, the new one signing in, the spent link explained. The hosted ride follows the allowlist step.

**Relationships.** Extends Slice 5d and D-009 (the Supabase project is ICC's). `scripts/admin-set-password.js` becomes the fallback and stays.

**Addendum (19 September 2026): the sign-ups control was found OFF on hosted; the owner step is now one scripted command that refuses to proceed while it is off.** The first live read of the hosted auth config (`scripts/supabase-auth-config.mjs`, Management API, dry run; confirmed by GoTrue's public `/auth/v1/settings`) returned `disable_signup: false`, against the "sign-ups disabled" recorded on 15 June 2026 and repeated above. The second 5d layer (`ADMIN_EMAILS` on every request) and RLS-with-no-policies on every public table mean nothing was exposed, but the inertness argument for a planted recovery fragment does not hold until the flag is flipped, and the redirect allowlist must not be set before it is. So: `node scripts/supabase-auth-config.mjs --apply --disable-signups` sends `disable_signup: true` with the Site URL and the four admin redirect URLs in one PATCH and proves all three by a read-back; without `--disable-signups` the script refuses (exit 2, nothing sent) while `disable_signup` is not a literal `true`. `test/hosted-auth-settings.test.js` (`ICC_HOSTED_IT=1`) is the standing read-back and is red until the flip. The wildcard entry stays a single `*` (Supabase's glob `*` cannot cross `.` or `/`, so it matches only a real `<deploy>--super-frangollo-c3a14a.netlify.app` host; the docs' `**` example would also match an attacker's host whose path carried the suffix). Lesson drafted as L-044.

## D-047 — Job photos live in a private Supabase Storage bucket, written best-effort after the booking is complete, read by the admin through short-lived signed URLs

**Status:** Draft for Ben's acceptance (built 19 September 2026 in the unattended session; the veto is one revert of the slice's four commits). Resolves the `TODO(slice5x/photos)` anchor planted by D-021 (Slice 5b, June 2026).

**Context.** Since Slice 5b a Postgres-mode booking's photo reached Mark only by email and in the PDF job card; the admin card said "No photo uploaded" for every live booking, because `job_photos` (init migration) wanted a Storage path and no bucket existed. The customer's photo is the one artefact the assessment, the quote and any later complaint (roadmap, Phase 2 "complaints handling") turn on, so the platform should hold it, not Mark's inbox.

**Decision.**
1. **One private bucket, `job-photos`**, created by migration `20260919120000_job_photos_bucket.sql` (`public = false`, a 4 MB object limit, exactly the four media types `validateBooking` accepts). `storage.objects` keeps Supabase's default RLS (enabled, no policy of ours), so only the service role, from the functions, can write an object or mint a URL. pgTAP `supabase/tests/job_photos_bucket_test.sql` pins the row, private, the bounds and the RLS state.
2. **The object path is server-derived**, `jobs/<job_id>/photo-<uuid>.<ext>` from the persisted job's id and the validated media type (`jobPhotoStore.photoObjectPath`); a non-uuid id or an unlisted type is refused before any call. Nothing the client sends reaches a path.
3. **Written last and best-effort.** `chat.js` calls `storeJobPhoto` at every success return of `handleBooking`, after the fail-closed insert, the calendar stamp, the PDF and both emails. It never throws, never changes the outcome or the emails, and its upload is raced against an 8 s deadline (supabase-js's storage upload takes no abort signal), so a slow or down Storage cannot hold the booking response or push the function past its own limit. The email still carries the photo: the guaranteed path is unchanged. Upload first, `job_photos` row second, so a row can never point at a missing object; a failed row insert removes the object.
4. **Read through signed URLs, one batch.** `bookings.js` signs every stored path in one Storage call (`createSignedUrls`, one hour, the admin session's own lifetime) and attaches `photo.url`; a signing failure leaves the url unset and the list still answers. `admin.html` renders the image only when the url starts with this project's Supabase origin plus `/storage/v1/` (the only place a photo can be), escaped, the same shape of guard as the calendar link (pinned). Uploads carry `cacheControl: 0` so an erased photo stops serving at once, not after a CDN max-age.
5. **Erasure is the API's job, not the cascade's.** Deleting a `jobs` row cascades `job_photos`, but a `storage.objects` row deleted by SQL orphans the bytes. `jobPhotoStore.deleteJobPhotos(supabase, jobId)` removes the objects, then the rows; whatever erases a job (SQL by hand today) must call it first. 6. **Privacy notice unchanged.** It already names photographs as data collected, Supabase (London) as the processor holding booking records, and the retention; Storage in the same London project is inside that disclosure. (Optional tightening for Ben: "records, including any photographs" in the Supabase line.)
