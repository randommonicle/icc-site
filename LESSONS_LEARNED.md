# ICC Platform — Lessons Learned

Hard-won gotchas and how we resolved them. Read before working near the chat proxy, bookings, email, or deploy config. Each has an ID (L-NNN) so other docs and code comments can reference it.

Some entries are seeded from the existing codebase and from the sibling ASH app, where the same class of problem already bit us. They are recorded here pre-emptively so we do not relearn them.

---

## L-001 — The chat origin check fails OPEN by default
When `ALLOWED_ORIGINS` is not set, `chat.js` derives a default allowlist and lets unrecognised origins through (logging a warning) rather than returning 403. The comment is explicit: the per-IP rate limit is treated as the real defence so a 403 storm never blocks customers. The consequence is that, until `ALLOWED_ORIGINS` is set in Netlify, the rate limit is the only thing standing between an attacker and your Anthropic bill. **Set `ALLOWED_ORIGINS` to the real production origins before launch.** Verify by POSTing from a disallowed origin and confirming a 403 once strict mode is on.

**Addendum (19 June 2026) — the safe-strict variant: strict mode no longer locks out the site's own deploy.** The blocker to turning strict mode on early was that setting `ALLOWED_ORIGINS` *replaced* the auto-detected Netlify origins, so it would 403 the live `.netlify.app` host and every deploy preview (you had to wait for the final custom domain and accept losing preview testing). Fixed in `buildAllowedOrigins()`: the site's own Netlify deploy origins (`URL` / `DEPLOY_URL` / `DEPLOY_PRIME_URL` — production, branch deploys, deploy previews) are now **always folded into the allowlist, even in strict mode**, so `ALLOWED_ORIGINS=https://intelligentclean.co.uk,https://www.intelligentclean.co.uk` enforces the public domain *and* keeps the `.netlify.app`/previews working. This only changes the strict branch; with `ALLOWED_ORIGINS` unset the allowlist is byte-equivalent to before, so current live behaviour is unchanged. `test/origins.test.js` pins both modes (incl. that a deploy preview is still allowed under strict mode, and that an arbitrary third-party origin is not). **Still true and unchanged:** the check is skipped entirely when a request carries **no `Origin` header**, so a non-browser script just omits it — the origin allowlist stops browser-based cross-origin abuse, not a determined scripted caller; the **per-IP rate limit remains the real defence** on the Anthropic-cost path. So this makes it *safe to enable* strict mode now, but enabling it is still a Netlify env change (deferred to the domain cutover by choice), and it is defence-in-depth, not the primary control.

## L-002 — Prompt caching only works if the cache prefix stays stable
`chat.js` sends the system prompt as two blocks: a large static block with `cache_control: ephemeral`, and a small dynamic block (assistant name, today's date, bookable dates). This is deliberate. If per-conversation or per-day content leaks into the cached block, the cache prefix changes every request and the discount evaporates. When editing the system prompt, keep anything variable in the second, uncached block. Cache hits cost roughly 10% of normal input — a large saving over a multi-message conversation.

## L-003 — Render all AI/booking output as inert text, never innerHTML
Both `index.html` and `admin.html` build AI replies and booking fields with DOM nodes (`createTextNode`) or an `escHtml`/`esc` helper, never `innerHTML`. This is the prompt-injection defence: a malicious or model-confused reply must render as text, not execute. The one intentional `innerHTML` use is the static typing-indicator markup. Do not introduce `innerHTML` for any content that originated from the model or a customer.

## L-004 — "Accepted by Resend" is not "delivered"
A 200 from the Resend API means Resend accepted the message, not that it reached the inbox. Actual delivery (delivered/bounced/blocked) lives in the Resend dashboard. Two specifics carried from the ASH app: corporate mail filters can hard-block certain content, and the sandbox sender (`onboarding@resend.dev`) has limited deliverability. Before relying on booking emails in the field, verify a real sending domain in Resend and set `OPERATOR_FROM` / `CUSTOMER_FROM` / `OPERATOR_EMAIL` to real addresses. Confirm an actual delivery, do not trust the API 200.

## L-005 — Netlify functions run in UTC; parse dates as local components
Booking dates are `YYYY-MM-DD` strings. `generateJobCardPDF` parses them into local date components (`new Date(y, m-1, d)`) precisely so the function's UTC runtime can never shift the printed day. Anywhere a date string is turned into a `Date` for display or day-of-week, parse the components explicitly rather than `new Date("YYYY-MM-DD")` (which is interpreted as UTC midnight and can render as the previous day in some timezones).

## L-006 — Rate-limit every expensive or abusable path, not just chat
Originally only `checkChatRateLimit` guarded the AI chat path; `check_availability` and `confirm_booking` had no cap, so a direct POST loop could block out calendar slots (slot-griefing) — `validateBooking` stops malformed payloads but not volume. **Resolved** on `hardening/phase0-pre-launch`: the limiter is now a reusable pure function `rateLimit(store, key, limit, windowMs, now)` (unit-tested in `test/hardening.test.js`) wrapped by `enforceRateLimit`, applied per-IP to all three POST actions — chat 30/hr, `confirm_booking` 5/hr, `check_availability` 60/hr — each failing open if Blobs are unavailable. Keep the rule going forward: any new endpoint that costs money or writes shared state gets a per-IP cap from day one. Caveat: this is per-IP and best-effort (shared/NAT addresses, IP rotation) — it is volume protection, not authentication. The origin allowlist (L-001) and `validateBooking` remain the other layers, and the real end-to-end check (a 429 against live Blobs) only happens on a deployed environment, not locally.

## L-007 — Netlify Blobs needs explicit auth for some deploy types
`getStore` is called with `siteID` and `token` (`NETLIFY_SITE_ID` / `NETLIFY_TOKEN`) because drag-and-drop deploys do not auto-configure the Blobs context. If Blobs reads/writes start failing after a deploy, confirm those two env vars are present in Netlify. The rate-limit and booking code fail open / log on Blobs errors, so a misconfiguration can be silent — check function logs, not just the UI.

**`NETLIFY_TOKEN` is a personal access token that expires — an expiry looks exactly like this failure.** The live token is set to expire **24 July 2026**. When Blobs auth starts failing with no deploy or config change to explain it, an expired token is the first thing to check. Because the failure is silent (rate limit fails open, so the chat endpoint keeps serving but loses its cost defence, L-001), nothing surfaces in the UI. Fix: regenerate the token (Netlify → User settings → Applications → Personal access tokens), update `NETLIFY_TOKEN` in the site env vars, and **redeploy** so the functions pick it up. A standing reminder is at the top of NEXT_SESSION.md; prefer a longer-lived/non-expiring token to stop this recurring annually.

**Addendum (30 July 2026):** the token above did lapse on schedule, and nobody caught it until a session was opened on 30 July 2026 — six days later. The standing reminder in NEXT_SESSION.md only gets read on session-open; there is no mechanism that fires on the calendar date itself. An out-of-repo calendar reminder would have caught this sooner than relying on session-open alone — moot now the replacement token is non-expiring; revisit only if a dated token is ever used again. Across those six days the Blobs-backed rate limit was presumably failing open exactly as described above (L-006) — nobody audited the function logs for that window, and with the site pre-launch and traffic effectively nil, treat that as a presumed state, not an audited clean record. The token was regenerated the same day, 30 July 2026.

A second, distinct failure mode surfaced during the regeneration: the new value was pasted into the work machine's `.env` with a leading space after `NETLIFY_TOKEN=`, producing 401s indistinguishable from an expired token — same symptom as this entry, different cause. What resolved it: parse the env value and check its length, prefix and leading/trailing whitespace **without ever printing the value itself**, then retry auth with the trimmed value. The same paste risk exists in the Netlify UI's env-var field; there, the only end-to-end proof is a live probe — the per-IP rate limit itself returning **429 on the 6th** deliberately-invalid `confirm_booking` request within the hour (`validateBooking` rejects the invalid payload regardless, so the probe never risks creating a real booking or holding a slot). Rule: verify a freshly pasted secret actually authenticates before declaring it updated.

## L-008 — Don't let a JSON.parse failure silently drop content
Carried from the ASH app. The booking flow depends on parsing a `BOOKING_READY:{...}` block out of the model's reply, and stored bookings are JSON in Blobs. A truncated or malformed JSON that is caught and swallowed makes a booking silently vanish with the customer none the wiser. Keep `max_tokens` generous for any response carrying JSON, log parse failures, and surface a fallback message ("call us on 01242 279590") rather than failing silently. The client already shows a phone-number fallback on booking error — preserve that pattern as the flow grows.

**Addendum (6 September 2026) — the predicted silent drop happened, from a cause this entry did not name, and the fallback it assumed was not actually wired.** The client extracted the payload with a non-greedy regex, `/BOOKING_READY:(\{[\s\S]*?\})/`, which captures only as far as the FIRST `}`. That held while every payload field was a scalar. D-004 (structured pricing, commit `88a0612`) added a nested `quote_lines` array, so the first `}` became the end of the first line item: the capture was truncated to invalid JSON, `JSON.parse` threw, and `processBooking` was never called. Every structured-pricing booking silently failed to confirm — no slot held, no emails, the customer left at "confirming your slot" with nothing after. The "phone-number fallback on booking error" this entry claimed the client already showed was NOT wired into that catch: it only stripped the marker and showed the pre-marker text. Two more specifics: the fallback number quoted above (01242 279590) is Regency's old line, superseded by ICC's **01452 452356** (D-030); and green unit tests plus a green build missed all of it because `handleBooking` is tested server-side with a pre-parsed object and nothing exercised the browser-side parse — it took a real post-deploy ride to surface it. **Fix (`fix/booking-ready-parse`):** replaced the regex with a brace-depth scan that ignores braces inside strings and tolerates trailing prose; wired a real "call us on 01452 452356 / email hello@" fallback when a marker is present but the payload will not parse; and added `test/booking-ready-parse.test.js`, which extracts the actual inline function from `book.astro` and runs it against the real `quote_lines` payload. **Rules reinforced:** a non-greedy brace match breaks the moment the JSON gains nesting — use a brace-aware scan; the browser-side parse is behaviour and needs its own test, not just the server handler; and when you assert a safeguard exists ("the client already shows a fallback"), enforce it with a test or it quietly won't (enforce-invariants-in-build).

## L-009 — Verify third-party and marketing claims before repeating them to customers
The Phase 0 assistant prompt repeated a supplier's marketing as fact: "WoolSafe approved", "76 dB / quieter than a vacuum", "EMV 409", "exothermic reaction draws dirt from the base of the fibre", "80% less water". A verified research pass (`docs/TEXATHERM_KNOWLEDGE_BRIEF.md`, on the Phase 1 branch) found the **"WoolSafe approved"** claim indefensible — Texatherm is absent from the WoolSafe directory, carries no mark or certificate number on its own product pages, and WoolSafe does not certify systems/machines/methods at all (only chemical products and accredited *service-provider companies*). The **76 dB** figure was refuted (the TC 170 page lists 63 dB(A)), the **machine model was wrong** (it is the EMV 401), and the performance figures are single-source manufacturer marketing. A Google AI Overview confidently asserted the opposite — it had blended Texatherm's real product names with Texatherm's own "safe for wool" marketing. **Rule:** any third-party, certification, or performance claim shown to a customer must be substantiated from a primary/independent source or attributed explicitly ("the manufacturer states…") — never asserted as fact, and never trusted from an AI summary. The distinction that bit us: a product being **"safe for use on wool"** (a supplier's in-house assessment, fine to state) is NOT the same as **"WoolSafe® approved"** (an independent certification ICC does not hold). The defensible USP is the science we can stand behind (low-moisture genuinely suits wool and natural fibres; residue attracts soil; honest stain limits), not borrowed marketing. `docs/TEXATHERM_KNOWLEDGE_BRIEF.md` is the single source (D-006) for both the site and the assistant — keep them aligned to it.

**Addendum (3 June 2026):** the same drift then surfaced in the *site*. The staged Astro `services.astro` and `history.astro` still asserted "WoolSafe approved", the exothermic "draws dirt from the base" mechanism, and the manufacturer figures as fact, even though PR #2 had already corrected the assistant. Fixing the claim in `chat.js` did **not** fix the duplicate copy elsewhere. **Rule reinforced:** when you correct a third-party or marketing claim, grep the whole repo against the brief (site content, not just the assistant prompt) and fix every occurrence in the same pass. Until D-006 is implemented as one shared source, the same fact lives in several files and drifts independently.

**Addendum (4 June 2026, evening):** the same class of unsubstantiated claim was also sitting in the site's *trust stats* (`500+ Cleans`, `98% Satisfaction`, `98% 5-Star Reviews` on the home and About pages) for a business with no track record yet. Removed on `feat/pre-cutover-polish` and replaced with capability/fact tiles (carpet types, trading days, deposit). The audit caught it by reading the rendered pages, not the assistant prompt, which is the L-009 reflex: **grep the built site, not just `chat.js`.** A grep-able `TODO(trust-stats)` anchor marks where real, substantiated metrics may go once they exist.

The Astro site (and the live `index.html`) inherited a blue navy base (`#1a3a5c` / `#0d2236`) that reads as ASH branding. The ICC logo is deep green + teal + gold. Follow-ups: Ben accepted the green provisionally and may want it toned down (change `--green-dark:#0c2c25` and `--green:#15564a` in that one place); the **live `index.html` is still blue** and should get the same treatment before or at cutover (a live change, needs deploy sign-off). ## L-011 — pgTAP `throws_ok` checks the error MESSAGE, not just the SQLSTATE
The Slice 2 schema test (`supabase/tests/schema_test.sql`) asserts that an overlapping booking is rejected by the `btree_gist` exclusion constraint. Written as `throws_ok(sql, '23P01', 'overlapping non-cancelled job is rejected')` it **failed**: given a third string argument, `throws_ok` treats it as the expected error *message* and compares it to Postgres's actual text. An exclusion-constraint violation emits Postgres's own wording (`conflicting key value violates exclusion constraint "..."`), which never matches the human string, so the assertion failed even though the correct error (SQLSTATE `23P01`) fired. **Fix:** pass `null` as the message (4th arg) so it asserts the SQLSTATE only, and put the human string in the description (5th arg): `throws_ok(sql, '23P01', null, 'overlapping ... is rejected')`. Verified: `supabase test db` passes pgTAP 10/10. Rule: when asserting a specific SQLSTATE in pgTAP, pass `null` for the message unless you genuinely mean to assert Postgres's exact wording.

## L-012 — Netlify builds deploy previews on a fresh commit, not on a PR base-retarget or reopen
Merging a stack of PRs where each targets the one below it (`#8 → #7 → #6 → main`) leaves the upper PRs with **no deploy preview**: Netlify only builds previews for PRs whose base is the production branch (`main`). The instinct is to retarget each PR to `main` as the one below merges, but retargeting via the API emits a GitHub `edited` event, which Netlify does **not** build. Closing and reopening the PR (a `reopened` event) also failed to trigger a build, because the head commit was unchanged and Netlify had never built that SHA as a preview against `main` — there was no `synchronize` event. The reliable triggers are a **fresh commit** on the branch (`synchronize`), or a manual `netlify deploy` from a checkout. On 7 June 2026, rather than dirty the history with throwaway commits, we verified Slices 1 and 2 **directly on production after merge**: Netlify atomic deploys never swap in a failed build (production keeps serving the last good deploy), `node --test` had already proved the modules load, and an immediate `/api/chat` + `/api/bookings` probe confirmed the live functions, with `git revert` as the undo. **Rule:** for a stacked-PR merge, decide the verification path up front — either verify on production (atomic-deploy + tests + live probe), or force each preview with a throwaway/empty commit. Do not assume a retarget or reopen produces a preview; it does not.

## L-013 — For the hosted ICC Supabase, use the CLI (account-wide token), not the MCP connector (single-org OAuth)
The Supabase MCP connector authenticates via OAuth scoped to **one organisation**. Ours was bound to the build-lead's personal `randommonicle's Org`, so once the dedicated **Intelligent Carpet Cleaning** org was created (10 June 2026), the MCP's `list_organizations` could not see it and could not create the project there — and re-authorising only lets you pick a single org, which would drop access to the other projects (PropOS, ASH). What works: the **Supabase CLI** authenticates with a **personal access token that is account-wide**, so it sees every org (and was already logged in on the machine). Stand up and drive the hosted ICC project through the CLI from the repo (`supabase link --project-ref qzcfgpfvzpynnjgriqqn`, then `db push` / `gen types` / `migration repair`), not the MCP. **Aside (same machine):** Claude runs here via the **desktop app**, so there is no `claude` (or `netlify`) CLI on PATH in a plain terminal — manage MCP connectors in the app's settings, and don't assume terminal CLIs exist.

## L-014 — The browser reads `data.content[0].text` and ignores `stop_reason`, so the server must return a single text block
`index.html` parses the `/api/chat` response as `data.content[0].text` (then scans that text for the `BOOKING_READY:{…}` block) and never inspects `stop_reason`. That contract constrains every server-side enrichment of the chat path. The moment the server runs a tool loop (Slice 4b `escalate_to_human`) or enables Citations (Slice 4c), the model's response is no longer a single text block: a tool round ends on `stop_reason:"tool_use"` with a `tool_use` block in `content`, and Citations splits the reply across multiple text blocks each carrying a `citations` array. Returning that raw shape would make the browser read only the first block (truncating the reply) or `undefined` (a `tool_use` block has no `.text`). **Fix (Slice 4b):** resolve tool rounds server-side (`runAssistantTurn`) and collapse the final message to one text block before returning (`withSingleTextBlock` in `chat.js` — concatenates text blocks, drops `tool_use`, passes API-error objects through untouched). When Slice 4c renders citation links to the customer, the *client* renderer must be extended to consume a structured citations payload (safe DOM `<a>`, sanitised `https`, never `innerHTML` — L-003); until then the normaliser keeps the single-text contract intact. **Rule:** any change that makes Anthropic return multiple or non-text content blocks must be normalised server-side (or the client updated in lockstep) — never assume `content[0].text` is the whole reply.

## L-015 — A wrong/absent operator address silently suppressed every operator email via Resend's account-level list
`OPERATOR_EMAIL` was set to `mark@intelligentclean.co.uk`, but that mailbox **never existed** — Mark's Workspace account was created as `mark_director@intelligentclean.co.uk` (only `ben@` and `mark_director@` appear in the Directory; the "mark@ owner mailbox" in the 10 June notes was aspirational). On 10 June the live TEST booking's **operator** email to `mark@` hard-bounced ("recipient not found"), and Resend added `mark@` to its **account-level suppression list**. From then on every send to `mark@` logged `Sent → Suppressed` in the same second — a 200 from the Resend API, never delivered (the purest form of L-004). Because the booking-confirmation operator leg and the new Slice 4b escalation both target `OPERATOR_EMAIL`, **both were silently dropped**; the 10 June "verified end-to-end" had only ever checked the *customer* email. Caught while preview-verifying #17: the escalation rendered perfectly in Resend but showed **Suppressed**. **Fix:** point `OPERATOR_EMAIL` at the real mailbox (`mark_director@`), remove `mark@` from Resend's suppression list, re-send on a fresh preview → **Delivered**. **Rules:** (1) verify **every** recipient leg of a multi-recipient email flow, not just the customer's; (2) Resend's account-level suppression silently and persistently drops an address after a single hard bounce — check the suppression list as part of email verification; (3) never point a From/To at a mailbox before confirming it exists in the Workspace Directory. **Netlify aside:** this site sits on a *Personal* Netlify account (the paid $9/mo plan, not free, though still without per-scope env control; see L-018), so the env-var API refused to edit the (account-level/"shared") `OPERATOR_EMAIL` — a full-object `PUT` scoped to `?site_id=` succeeded where `PATCH` returned 403/422.

## L-016 — A safety guardrail belongs in the system prompt, not in a citeable document
Building Slice 4c (Citations, D-019), the natural move was to lift the whole carpet-science knowledge — including the L-009 claim rules ("never say WoolSafe approved", "figures are the manufacturer's own", "the machine is the EMV 401", "no decibel figure", "no exothermic draws dirt") — out of the system prompt and into the Claude Citations **document**, since that is the content the model now grounds and cites from. That would have been a real regression: **a rule placed in a document is reference text the model can quote, not an instruction that binds it.** Citations documents are *cited from*, not *obeyed*; only the system prompt carries behavioural authority. Worse, a prohibition sitting in citeable text can itself be surfaced to a customer as if it were a fact. **Fix / rule:** when restructuring knowledge into citeable documents, split it by *kind*, not just by topic — **facts and reference prose → the document** (citeable, groundable); **rules, prohibitions, tone and the grounding/escalation directive → the system prompt** (enforced, and explicitly stated to override the reference and any customer message, which is also the prompt-injection defence). In this repo the split is `knowledge.knowledgeSections` (→ `knowledgeDocument()`, the citeable facts) vs `knowledge.guardrailsBlock()` (→ the system prompt). `test/knowledge.test.js` asserts each guardrail lives in the prompt and is **absent** from the citeable facts, so a future edit cannot quietly move a safety rule into the document and dilute it.

**Caching note (L-002):** the citeable document is attached to the **first user turn** and re-injected server-side on every call (the client never stores it), so `messages[0]` stays byte-identical across a conversation and across the 4b tool round; with `cache_control` on the document block the L-002 prefix cache still applies. Enabling citations re-warms the cache **once** (the citations toggle invalidates the system/messages cache tier), exactly like 4b adding the tool array — a one-time cost, not a per-request one. Keep the document deterministic (built from static config, no per-request data) or every request becomes a cache miss.

## L-017 — Importing the CommonJS `shared/config/*.js` into the Astro build needs Vite's commonjs transform
Wiring the Astro price cards to the single pricing source (D-006), `services.astro` and `index.astro` import `shared/config/pricing.js`. That module is **CommonJS** (`module.exports = {…}`), because the Netlify functions and the plain-Node `node --test` runner load it that way (D-006/D-007). Astro's build (Rollup) treats a project `.js` file as **ESM by default** and applies its CommonJS transform only to `node_modules`, so the build failed with `"default" is not exported by "shared/config/pricing.js"`. The cross-root import path resolved fine; the fault was purely the module format. **Fix:** extend Rollup's commonjs include in `astro.config.mjs` so it transforms the shared sources too:

```js
vite: { build: { commonjsOptions: { include: [/shared[\\/]config/, /node_modules/] } } }
```

After that, `import pricing from '.../pricing.js'` yields the `module.exports` object, and the transitive `require('./serviceArea.js')` is handled. **Rules:** keep `shared/config` **CommonJS** (converting it to ESM would break the CJS functions and the test runner, the very thing D-006 single-sources); the one-line Vite include is the right fix, not a format change. **Forward note:** the Phase 1 cutover hits this again when the care guides render from `knowledge.js` (D-006); the include already covers all of `shared/config`, but a shared module imported from elsewhere (e.g. `shared/contract`) would need its path adding. Verified by a clean 22-page `npm run build --prefix site` with the figures correct in the built HTML.

**Dev-server note (22 June 2026):** the same CommonJS root cause also breaks `astro dev`. Any page importing `shared/config/*.js` throws `ReferenceError: require is not defined` (e.g. `pricing.js:16`, where it `require`s `serviceArea.js`) because Vite's **dev SSR module runner** evaluates the CJS module as ESM, and the build-time `commonjsOptions.include` above does **not** apply to the dev SSR path. The production **build** is unaffected (proven live). So to preview the site locally, **`npm run build --prefix site` then `npm run preview --prefix site`** (astro preview serves `dist`), **not** `npm run dev`. This is how the hero-logo change (22 June) was verified locally.

## L-018 — Netlify env vars via the API on the paid $9 Personal plan: no per-scope control; POST creates, PUT updates, and a redeploy bakes them for functions

Enabling Slice 5a, setting `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` through the Netlify env-var API first failed with `403 {"message":"Upgrade your Netlify account to set specific scopes"}` because the body included `scopes:["functions"]`. Per-scope control is a higher-tier feature; the **paid $9/month Personal plan** (this site's plan, correcting L-015's "free-feature" aside) can only set a variable for **all** scopes. **Fix:** omit `scopes` so the var applies to all scopes. That is how the existing secrets are already stored, and it is safe here because nothing in the site *build* references the service-role key, so it never reaches client output (the value lives only in the function runtime, not the deployed assets).

Mechanics confirmed this session, all site-scoped with `?site_id=`:
- **Create:** `POST /api/v1/accounts/{account_slug}/env?site_id={site_id}` with a JSON array of `{key, values:[{value, context:"all"}]}` and **no** `scopes` → `201`.
- **Update one key:** `PUT /api/v1/accounts/{account_slug}/env/{key}?site_id={site_id}` with the single object → `200` (the L-015 method).
- **Redeploy:** `POST /api/v1/sites/{site_id}/builds` triggers a production build.
- **Env changes are baked at deploy:** a function only sees a new or changed value after a redeploy. Verified by flipping `OPERATOR_EMAIL` to a test address, redeploying, confirming, then restoring it with a second redeploy. So "set the var" and "the live function uses it" are two steps.

The `account_slug` comes from `GET /api/v1/sites/{site_id}` (`.account_slug`). Cross-ref L-015 (same Personal-account env API).

## L-019 — Apply a hosted Supabase migration with the Management API when you have the access token but not the DB password

Enabling Slice 5b needed one DDL migration (`alter table jobs alter column postcode drop not null`) on the hosted project, but `supabase db push` and `supabase migration repair` both connect to Postgres directly and so need the **database password**, which was not in the repo `.env` (only `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`), and the worktree was not `supabase link`ed. The service-role key is a PostgREST/GoTrue JWT, **not** a Postgres role password, so it cannot run DDL over the REST API either.

**What works:** the **Supabase Management API** query endpoint — `POST https://api.supabase.com/v1/projects/{ref}/database/query` with body `{"query":"<sql>"}` and `Authorization: Bearer $SUPABASE_ACCESS_TOKEN` — runs arbitrary SQL server-side (it is what the dashboard SQL Editor uses). The **account-wide personal access token** is what the CLI authenticates with; here it was already present as `SUPABASE_ACCESS_TOKEN` in the environment, so a one-off `fetch` applied the ALTER (HTTP 201) and a follow-up `select … from information_schema.columns` / `pg_constraint` catalog-verified it (`is_nullable=YES`, invariants intact) — the db-migration-verification check, done remotely.

**Two gotchas:** (1) the Management API **bypasses migration history** (`supabase_migrations.schema_migrations`), so `db push` will later see the migration as pending and re-apply it — fine here because `ALTER … DROP NOT NULL` is **idempotent** (a no-op on an already-nullable column, no error), but for a non-idempotent migration you would corrupt state, so prefer `db push` (clean history) when the DB password is available and only reach for this when it is not, favouring idempotent SQL. Record the migration with `migration repair --status applied <version>` once the password is to hand. (Done for 5b on 14 June: after `SUPABASE_DB_PASSWORD` was added to `.env`, `supabase link` + `migration repair --status applied 20260614100000` reconciled hosted history with no schema change — `migration list` then showed all four migrations Local + Remote.) (2) **Quoting:** running the SQL through `node -e '…'` inside a bash single-quoted command silently strips the SQL's own single quotes (`'public'` → `public` → `column "public" does not exist`); use a quoted heredoc (`node <<'NODE' … NODE`) or a temp script file so string literals survive. The DDL itself (no quotes) ran fine; only the verification `select`s broke until re-run via heredoc.

## L-020 — An input-minimisation guarantee must be enforced at the boundary, not just asserted
Slice 5e-2's handoff draft generator (`handoffs.js` `draftReplyForHandoff`) is sent **only** the captured `handoff_question`, never the customer's name/contact/transcript — the input-minimisation property the design claims (UK GDPR Art.5(1)(c)). But that field is written by the chat model when it calls `escalate_to_human`, with nothing stopping it folding "Jane on 07700 900123 asks…" into the question text. So "only the question crosses the boundary" was true of the *field we send*, not of the *data inside it* — the guarantee rested on the model behaving, not on the code. Caught in the 5e-2 code review (finding A1). **First fix:** tightened the tool's `question` description to forbid names/contact (they have dedicated fields), pinned by a test in `test/escalation.test.js`. That lowers the likelihood but is still a soft control. **Stronger fix if this surface ever carries higher-risk data:** redact PII (email/phone/UK-postcode regex) from `handoff_question` before the model call (a `TODO(prelaunch/email-identity)` sibling). **Rule:** when a design asserts that only field X reaches an external model, check what can actually end up *in* X. If X is free text a model or user populates, the minimisation must be enforced (a scrub, or a schema the producer cannot widen), not assumed — an asserted guarantee with no code behind it is a comment, not a control. Mirrors L-016 (a rule binds only where it is enforced).

## L-021 — Fail-closed send and never-double-send pull in opposite directions; pick the safer failure
Slice 5e-2 marks a handoff reply `sent` **only after** Resend returns 2xx (fail-closed — a crash never records a reply that did not go; L-004/L-008). The review (finding A2) noted that this same ordering lets two concurrent sends both pass the "already sent?" pre-check and both email the customer before either marks the row (a read-then-write race). The two properties cannot both be fully satisfied without an intermediate **claim** state: marking `sent` *before* the email (to claim the row) would prevent the double-send but reintroduce the lost-reply failure if the send then fails. Faced with that, the worse outcome for a customer reply is **silently not sending** (the customer hears nothing while Mark believes they were answered), so we kept fail-closed and accepted the residual double-email window — which needs two simultaneous operators on a single-operator admin. A conditional mark (`status<>'sent'`, checking the affected-row count) was added so a lost race is at least **detected** (409) rather than silently double-recorded. **The clean fix, deferred:** a `'sending'` `message_status` value to claim the row atomically before the send, with rollback on failure (needs a migration). **Rule:** when "never lose it" and "never duplicate it" conflict on an outbound side effect, decide which failure harms the recipient more and design for that one; only a real claim/lock (a DB state transition, not a read-then-write) removes the race, and that is a deliberate, tested change, not a default.

## L-023 — A port is only finished when it still consumes everything the server sends; nothing tested the browser client, so a feature loss survived a month

## L-022 — "Is this branch merged?" needs a content check, not `git branch --merged`, and a stale worktree can hide six weeks of drift
The 2026-07-19 home-machine tidy-up found nine stale branches and four abandoned worktrees. The only reliable confirmation was checking the branch's actual *content* on main (the A4 privacy link in `handoffs.js`, the A5 `retention.js`/`purge-handoffs.js` files). **Second:** the `friendly-dewdney-464b0d` worktree showed 32 modified files, which looks like unsaved work worth rescuing. It was the opposite — a 5 June snapshot on the pre-monorepo `netlify/functions/` paths, *missing* every test and migration added since. A raw `git diff --stat` against its own old base made it look like 4,700 lines of new work; diffing it against `main` showed 11,456 deletions, i.e. how far behind it was. The decisive test was semantic: extract every top-level identifier from its files and grep main for each. It blocks `Remove-Item` and `git worktree remove` with "Directory not empty" and needs the reserved-name escape: `cmd /c 'del /f /q "\\?\C:\full\path\nul"'`.

## L-024 — A cadence change must reach the availability COLLISION logic, not just the offered grid
D-027 added half-hour start times (:30). The offered-grid generator and `validateBooking` were moved to the new cadence, but `availabilityFromJobs` / `checkAvailability` still computed slot occupancy at WHOLE-HOUR granularity (it floored each booked job to its start hour and spanned whole hours). Consequence: a 12:30 one-hour job occupies 12:30 to 13:30, but the model only marked the 12 o'clock block, so the engine still OFFERED the 1pm start, which the minute-precise DB exclusion constraint (`span_minutes`) then REJECTED at confirm with 23P01. That is exactly the F2 failure (the site sells a slot the engine rejects) that D-027 exists to prevent, reintroduced one layer down. It was latent, not live, because production still ran the old whole-hour app; it would have shipped the moment the branch deployed. **Fixed** in `615ec7a`: `availabilityFromJobs` returns `[start, end)` minute ranges and `checkAvailability` drops an offered start only when its own span overlaps a booked span, mirroring the DB constraint. **Rule:** when you change the granularity of a booking cadence, change every downstream occupancy/collision calculation to match, not just the offered grid and the acceptance gate; a coarser collision check silently under-blocks and offers unbookable slots. **Process note:** this session's first pass DISMISSED the prior handover's "make availability minute-aware" TODO as resolved-by-design, reasoning from structure; it was an independent cross-agent reviewer (GPT) that produced the concrete 12:30/13:00 counterexample. Extends the F2 single-source lesson (D-006, the trading-hours work) down to the collision layer.

## L-025 — Rotating a capability token revokes the old link only if the consuming operation BINDS to the token hash
D-027's admin "resend" mints a new action token, stores its SHA-256 hash and overwrites the old one; the plaintext of the old token is gone. The public accept/decline endpoint VERIFIED the presented token against the stored hash and THEN ran a compare-and-set matching only `id + confirmation_state='awaiting_operator' + operator_action_token_used_at IS NULL` — it did NOT re-check the hash inside the CAS (`bookingAction.js` → `decideProvisional`). Consequence: a stale-link request that loaded and verified the OLD hash, then paused between verify and the CAS while an admin resend rotated the hash, would still succeed, because the CAS never re-examined the hash. So "rotation invalidates the old link" held for a FRESH request (it loads the new hash and fails `tokenMatches`) but NOT for one already in flight — the exact window a revocation is meant to close. **Fixed** (`d31c700`): `decideProvisional` takes an optional `expectedHash`; the public path passes the hash it verified, so the CAS gains `AND operator_action_token_hash = <verified hash>` and a rotation mid-flight yields 0 rows → 409. Resend is itself a CAS on the OLD hash, so concurrent resends are single-winner and a resend cannot rotate an already-decided job. The admin decide path passes NO hash (its authority is `requireAdmin`, not a token). **Rule:** when a capability can be ROTATED, the operation it authorises must bind its atomic write to the exact token/hash it verified — check-then-act over a mutable credential races the rotation, and re-verifying up front is not enough. Surfaced by the cross-agent review (GPT), 2026-09-02.

## L-026 — A "claim" that is not atomic is not a claim; send-then-log leaves no durable trace on a path with no CAS
D-027's provisional accept/decline notify was described as "claim-then-send", but the implementation TRANSITIONED the booking (the jobs CAS), then SENT the customer email, then INSERTED a `messages` row 'sent'/'failed' — and only when `RESEND_API_KEY` and an email address were both present. Two gaps: with no key, NO row was written at all, so a resolved booking left no trace of an un-sent notice; and a crash after the CAS but before the insert left a resolved booking with no row either. For the DECISION this is safe (the jobs CAS gates it to one winner, so at most one notify runs), but the admin recovery the design promised — "a failed customer notice must be visible and retryable" — did not exist: nothing surfaced a missing/failed notice, and "resend" only re-issued the OPERATOR link, never the customer notice. **Fixed** (`d31c700` + `2613dff` + `ed6081f`): `notifyCustomerOutcome` ALWAYS logs a row (sent/failed, including no-key / no-email); the admin annotates each provisional job's notice status; and a `retry_customer_notice` action re-sends the outcome for a RESOLVED booking whose notice is not 'sent', derived from the FINAL `confirmation_state` and read-then-send idempotent. The crash case is recovered by a READ MODEL (resolved state + no 'sent' row → "not notified" + a retry button), not a pre-send draft claim. **Rule:** a downstream side-effect (an email) whose only guard is a post-hoc log is not "claimed"; on a path with NO atomic CAS gating the send — a RETRY does not mutate `jobs` — a concurrent double-fire is possible, so bound it with a client button-disable + a cap, or a pre-send claim on a unique row (a `sending` status + a partial unique index), matched to how much a duplicate actually harms. Surfaced by the cross-agent review (GPT + Gemini), 2026-09-02. **Built (2026-09-03):** the stronger option named above, a pre-send claim on a unique row, was subsequently built (DECISIONS D-027 addendum 2026-09-03): a `sending` `message_status` value + a partial unique index on `(job_id, kind)`, claimed in JS before the send, with a 15-minute stale reclaim so a dead sender cannot strand the notice. Proven single-winner by guarded integration against real Postgres for both the fresh-insert and the reclaim interleavings. Why the claim is not `.upsert()`: L-028.

## L-027 — `supabase start` runs against a PERSISTED volume; `supabase db reset` after any migration or you test a ghost schema
Running the pgTAP suite (`supabase test db`) and the guarded integration tests locally on 2026-09-03, the `confirmation_state` cases failed with `column "confirmation_state" does not exist`, and a pre-existing, untouched test (`messages_handoff_reply`) failed the same way, yet the earlier `postcode`-nullable migration WAS present. Cause: the local Supabase Docker volume was initialised around mid-June and PERSISTS across `supabase start`; `supabase start` applies migrations only when it first creates the database, so every migration added AFTER the volume was created (both D-027 migrations and the June `messages_handoff_reply`) was never applied. The local stack was silently testing a stale schema, and a green-looking run would have proved nothing about the real change. **Fixed** by `supabase db reset` (drops and re-applies all migrations from scratch), after which pgTAP and the integration tests passed. **Rule:** after adding or changing any migration, run `supabase db reset` before trusting a local pgTAP or integration run; `supabase start` / `supabase test db` alone can run against a ghost schema, and a passing test on the wrong schema is worse than a failing one because it manufactures false confidence. ## L-028 — supabase-js / PostgREST upsert cannot target a PARTIAL unique index; drive the claim from code
D-027's strict single-winner notice enforces one `messages` row per `(job_id, kind)` with a PARTIAL unique index (provisional kinds only, so the several email/sms rows a job legitimately accrues are unaffected). The obvious idempotent write is `supabase.from('messages').upsert(row, { onConflict: 'job_id,kind' })`, but supabase-js emits `ON CONFLICT (job_id, kind)` with NO predicate, and Postgres will not match that to a PARTIAL index: the conflict inference needs the index's `WHERE` clause, which PostgREST cannot express, so the upsert errors with "no unique or exclusion constraint matching the ON CONFLICT specification". A NON-partial unique on `(job_id, kind)` was not an option (it would forbid the legitimate multiple email/sms rows). **Fixed** by doing the claim in application code as a reclaim-UPDATE-then-INSERT against the partial index: UPDATE a reclaimable row to `sending`; if none matched, INSERT, and treat a `23505` as "another sender holds it". The partial index still gives the atomic single-winner guarantee at the INSERT. **Rule:** a partial unique index cannot be a PostgREST upsert conflict target; when you need partial uniqueness (idempotency scoped to a subset of rows) with an idempotent writer, drive the claim from code (UPDATE-then-INSERT, or an RPC that spells out `ON CONFLICT ... WHERE`), never from `.upsert()`. Proven correct by guarded integration tests for both the fresh-insert and the reclaim interleavings. Surfaced building the D-027 strict retry, 2026-09-03.

## L-029 — `fetch` never throws on an HTTP error, so a Resend non-2xx booking send was swallowed as success
The website booking path (`handleBooking` in `chat.js`) sent Mark's operator email and the customer email with `Promise.all([fetch(...), fetch(...)])`, read `res.json()`, and returned `success:true` without ever checking `res.ok`. `fetch` resolves rather than throws on a 4xx/5xx, so a rejected Resend send left its error object sitting unread in the returned `markEmail`/`customerEmail` field while the booking reported success and the customer was told "Mark will confirm the time". The whole D-027 provisional feature hinges on that operator email, so a silent failure would strand a held slot with nobody notified and no log. The unit tests could not catch it: the `global.fetch` stub returned `{ json: async () => ({ id: "fake" }) }` with no `ok`/`status`, modelling only the success shape, so the failure branch was untestable because it did not exist. It surfaced on the D-027 live ride (2026-09-04), the first real end-to-end run; the sends in fact succeeded (`markEmail`/`customerEmail` ids were visible in the browser network log), but chasing an apparently-missing email exposed the unchecked `res.ok`. **Fixed** at both `chat.js` send sites, the booking send and `sendEscalationEmail`: check `res.ok`, log each failure, surface an `emailStatus:{operator,customer}` flag, and make the customer message honest when a send fails, while still returning `success:true` because the booking (the held slot) is already persisted. The other Resend callers (`bookingDecision`, `bookingAdmin`, `reviewRequest`, `handoffs`) already failed closed on `!res.ok`. The three test stubs were updated to `{ok:true,status:200,...}` and two failure tests added that a pre-fix run cannot pass. **Rule:** `fetch` does not throw on HTTP errors and a 200 is not delivery, but a non-2xx IS a definite send failure, so always check `res.ok` on an outbound call, and give the test double the failure shape (`ok:false`) or the mock silently guarantees the bug it is meant to guard. And a signal only counts as surfaced once a consumer reads it: the first cut set an `emailStatus` flag the browser booking clients ignored (they hard-coded "emails have been sent"), so a pre-deploy code review had to wire `book.astro` and `index.html` to display it, since a server-side flag nobody reads is still silent to the customer. Surfaced on the D-027 live end-to-end ride, 2026-09-04; the client-display gap was caught by the pre-deploy review.

## L-030 — `[skip ci]` is read on the TIP commit and skips the WHOLE build, so a code fix pushed behind a `[skip ci]` docs commit silently does not deploy
On 2026-09-04 the pending operator-email fix (`7626bfc`) was pushed to `main` together with a handover-doc commit (`710a4ba`) whose message ended `[skip ci]`. That docs commit was the TIP of the push. Netlify evaluates the head commit of a push to decide whether to build, saw `[skip ci]`, and skipped the build for the ENTIRE push, even though `7626bfc` (real code) sat behind it. The result was the worst kind of quiet: `git` showed `origin/main` advanced to include the fix and everything "pushed", but the live site still ran the previous deploy (`e2b71e9`) and the fix was NOT live. Confirmed via the Netlify deploys API (latest deploy still `e2b71e9`; no deploy at `7626bfc`/`710a4ba`). The handover's own stated next action, "push `main` to deploy `7626bfc`", could therefore never have worked as written, because the docs `[skip ci]` had been committed on top of the fix. **Fixed** by triggering a manual build via the Netlify API (`POST /sites/{id}/builds`), which ignores `[skip ci]` and builds the current head (which includes the fix); the deploy reached `ready` at `710a4ba` and the live checks passed. **Rule:** `[skip ci]` / `[skip netlify]` is judged on the HEAD commit of a push and suppresses the build for the whole push, not just that commit, so never leave a `[skip ci]` commit as the tip when an un-deployed code/content change sits behind it.
